# linaX(uno) ― Arduino Uno（ATmega328P）に載せた Unix 系 OS

2026年11月26日 20:17

<p><img src="../assets/rina-chan.png" alt="リナちゃん" width="240"></p>

## 概要

linaX(uno) は、通常の Arduino Uno（ATmega328P、SRAM 2 KB、フラッシュ 32 KB）に載せた Unix 系 OS です。ベアメタルで動作し、カーネル、プリエンプティブなプロセス、exec、ファイルシステム、シェルを持ちます。シェルもコマンドも、exec で起動される実プロセスです。コマンドは BusyBox 方式で 1 つのイメージを共有しますが、エントリはコマンドごとに分かれ、実行のたびに個別のプロセスとして起動されます。「シェル風の画面」ではなく、本物のプロセスモデルで動くことを設計の絶対条件にしました。いわゆる張りぼて（コマンドを内蔵しただけの見かけのシェル）ではありません。ps でプロセスの状態が見え、シェルが exit すれば init が起動し直し、コンパイラで作ったプログラムも 1 プロセスとして exec されます。

さらに、基板上で C のソースを書き、その場でコンパイルして実行する仕組み（cc コンパイラ＋バイトコード VM）まで載せています。ATmega328P は RAM 上のコードを実行できず、アプリ領域からフラッシュへも書けないため、コンパイル結果はネイティブコードではなくバイトコードとし、VM が解釈実行する方式を取りました（自作の C インタプリタ LiveC と同じ発想です）。

周辺機器のサポートとして、GPIO の入出力と I2C マスタもシステムコールで提供しています。gpio／i2c コマンドから、ピンの操作と I2C デバイスの読み書きができます。

LinaX は、各種マイコンへ Linux／Unix 系 OS を載せる一連の試みの名前で、(cyd) は初代 ESP32、(C61) は ESP32-C61 向けです。本機 (uno) はその最小構成版にあたります。

動作環境は次のとおりです。

- 対象：Arduino Uno（ATmega328P、16 MHz）
- コンソール：UART0（USB シリアルブリッジ経由、115200 bps）
- 書き込み：標準ブートローダ（Optiboot）経由、avrdude で通常書き込み
- 開発言語：C + アセンブリ（avr-gcc、Arduino コア不使用）
- バージョン：0.8

既存の最小級 Unix と必要 RAM を比べると、次のようになります。

| システム | 必要 RAM の目安 |
|---|---|
| linaX(uno) | 2 KB（カーネル使用量 1,982 バイト） |
| LSX（Unix V6 を削った最小構成） | 約 40 KB |
| FUZIX | 数十 KB 級 |
| uClinux | MB 級 |

プロセスと exec を備えた Unix 系 OS が RAM 2 KB で動く例は、これまで無かったはずです。ATmega328P には MMU が無く、アドレス空間も 64 KB しかありません。載せるのではなく、削り切る設計が要ります。

### アーキテクチャ

プロセスは最大 3 つです。

- PID0：カーネル（アイドル兼 init 役）。起動時にシェルを exec し、シェルが終了すると再起動します
- PID1：シェル（/bin/sh、ユーザプロセス）
- PID2：シェルから起動されるコマンド（子プロセス）

スケジューラはラウンドロビンで、タイマ割り込みは 100 Hz、タイムスライスは 10 tick（100 ms）です。子プロセスが終わるとゾンビになり、親の wait で回収されます。終了コードも渡ります。

コンテキストスイッチはアセンブリで書き、Timer1 比較一致割り込みの naked ハンドラと、任意に呼ばれる yield が、レジスタ保存・復元の核を共有しています。保存フレームは 35 バイト（全レジスタ＋SREG＋戻りアドレス）で、復帰は両経路とも RETI です。プロセス生成時は、このフレームをスタック上に偽造して「割り込みから復帰したことにする」ことで新規プロセスを開始します。

メモリ分離は MMU が無いためソフトウェアで行います。

- 全ユーザプログラムは、共通の 256 バイトのデータ領域（ウィンドウ）にリンクします（.data と .bss はこの領域内に収めることがビルド条件）
- プロセスごとに 256 バイトの退避領域を持ち、スケジューラがプロセスを切り替える際、必要なときだけウィンドウの中身を入れ替えます（遅延スワップ）
- スタックはプロセスごとに 192 バイト
- プログラムのコードと文字列はフラッシュ側に置き、RAM はデータだけに使います

システムコールは、フラッシュの固定アドレス 0x2000 に置いたゲート（JMP テーブル）経由で呼びます。ユーザプログラムはゲートのアドレスを関数ポインタとして呼ぶだけです。

| 番号 | 名前 | 内容 |
|---|---|---|
| 0 | exit | 終了コードを持って終了 |
| 1 | write | fd へ書き込み（コンソール／ファイル） |
| 2 | read | fd から読み込み（コンソール／ファイル） |
| 3 | yield | 自発的にスケジューラへ |
| 4 | getpid | 自分の PID |
| 5 | sleep | tick 単位でスリープ |
| 6 | exec | パスと引数で別プログラムを起動 |
| 7 | wait | 子プロセスの終了を待ち、回収 |
| 8 | open | ファイルを開く（読み取り） |
| 9 | close | 閉じる |
| 10 | readdir | ディレクトリのエントリを列挙 |
| 11 | argv | 自分の引数文字列を取得 |
| 12 | tasks | プロセス表を取得（ps 用） |
| 13 | openw | /tmp のファイルを開く（書き込み／追記） |

ファイルシステムは 2 つあります。フラッシュの 0x4000 に置いた読み取り専用の romfs（ヘッダと 24 バイトのエントリ表だけの単純な形式、現在 18 エントリ、11,160 バイト）と、RAM 上の tmpfs（/tmp、4 ファイル×96 バイト、電源を切ると消えます）です。exec は romfs のプログラムイメージを読みますが、/tmp のファイルは先頭 2 バイトのマジック「UB」を見てバイトコードと判別し、/bin/vm 経由で実行します。

ユーザプログラムを書くときの決まりごとが 1 つあります。文字列リテラルはフラッシュ側にあり、システムコールの引数や libc の文字列関数は RAM（データ空間）のポインタを要求します。リテラルをそのまま渡すと、相手は SRAM のゴミを読んでしまいます。そのため、リテラルの表示はフラッシュ対応の uputs、比較は ucmp、コピーは ucpy を使い、RAM に必要な文字列は .data の配列として宣言する、という規律で統一しています。

### サイズ

- カーネル＋romfs の結合イメージ：27,544 バイト（アプリ領域の上限 0x7E00 = 32,256 バイト以内、残り 4,712 バイト）
- カーネルの RAM 使用量：1,982 バイト（SRAM 2,048 バイト中）

## 製作過程

### 出発点

対象は通常の Arduino Uno（ATmega328P）です。SRAM 2 KB には、FUZIX 級の既存 Unix を移植する余地はありません（実測でも確認しました）。そこで、プロセスと exec を備えた最小の Unix 系 OS を、カーネルから自作することにしました。

### M0：ベアメタル起動

バナー表示、100 Hz tick、UART エコーだけの最小イメージ（706 バイト）を作り、Optiboot からの引き継ぎ（割り込みベクタとウォッチドッグの始末）を確認しました。実機で起動とエコーを確認済みです。

### M1：スケジューラ

タイマ割り込みによるプリエンプティブなコンテキストスイッチと、ラウンドロビンスケジューラを実装しました。2 つのスレッドが交互に動くことを確認しています。

### M2：ユーザプロセス

プロセスの生成・終了の仕組みを作りました。exec でユーザプログラムを起動し、exit の終了コードを親が wait で回収する一連のライフサイクルと、データウィンドウの入れ替えを確認しています。

### M3：romfs とシェル

romfs を載せ、シェルを PID1 の実プロセスとして実装しました。ls、cat、echo、uname、ps はそれぞれ別プログラムとして /bin に置き、exec で起動します。open／readdir／argv のシステムコールを追加し、相対パスの解決やカレントディレクトリの保持はシェル側で行います。実機で対話シェルの動作を確認済みです。

起動時には LinaX の ASCII アートロゴ（(cyd) と同じもの）を表示します。フラッシュ常駐のため RAM は消費しません。

この段階までの名称は unox でしたが、LinaX 系の命名に統一するため linaX(uno) へ改名しました。

### M4：基板上コンパイラ

/tmp（tmpfs）と、シェルの echo によるリダイレクト（> と >>）を実装し、ファイルを基板上で書けるようにしました。その上で、

- cc：C サブセットをスタック VM 用バイトコード（UB 形式）へコンパイルするコンパイラ
- vm：バイトコードの実行ランタイム。exec が UB マジックを見分けて vm 経由で起動

を作り、「echo で書く → cc でコンパイル → 実行」の流れを基板上で完結させました。続いて、複数行をまとめて書けるヒアドキュメント（`echo > /tmp/a.c <<EOF` … `EOF`）もシェルに追加しています。実機で a=7;／print a*6; のプログラムをコンパイル・実行し、42 が出ることを確認済みです。

M5 では周辺機器のサポートを足しました。システムコールの空き枠（ゲート 14／15）に GPIO と I2C を割り当て、カーネルに sys_gpio／sys_i2c を実装しています。GPIO は Arduino と同じピン番号（0〜19、14〜19 が A0〜A5）で入力／出力／読み／書きができ、I2C は内蔵 TWI ハードウェアによるマスタ転送（100 kHz、A4=SDA／A5=SCL、書き込み→リピートスタート→読み取り対応）です。応答の無いスレーブで固まらないよう、ポーリングにはタイムアウトを付けています。操作用のコマンド gpio／i2c（バススキャン付き）も /bin に追加しました。simavr では、ピンの出力と読み戻し（hi で 1、lo で 0）、デバイスの無いバスでの scan（none の表示）と読み取りエラー（no ack）まで確認済みです。実機での確認はこれからです。

M6 では待ち（ディレイ）を足しました。点滅のような動きには待ちが要りますが、それまでカーネルの sys_sleep を呼ぶ口がシェルにも cc にもありませんでした。/bin/sleep（単位は 10 ミリ秒）と、cc の wait 文（ミリ秒）・pin 文（ピンを出力にして値を書く）を追加し、vm 側に対応する命令を入れています。これで、基板上の C だけで `while(1){ pin 13, 1; wait 500; pin 13, 0; wait 500; }` という Lチカが書けます。simavr では、pin 文で書いたピンの状態を gpio コマンドで読み戻して 1 になることまで確認済みです。なお、無限ループのプログラムを途中で止める仕組み（Ctrl+C）はまだ無く、止める場合はリセットします。

M7 では Ctrl+C を実装しました。カーネルの UART 受信処理が Ctrl+C（0x03）を受けると、親が wait で待っている実行中プロセス（フォアグラウンド）に終了フラグを立て、スケジューラがそれを終了コード 130（128＋SIGINT）のゾンビに変えて親を起こします。プロンプトで押した場合は行入力側が受け取り、入力中の行を破棄します。ヒアドキュメントの入力中も Ctrl+C で中断できます。simavr では、長い sleep の中断、点滅プログラムの中断、プロンプトでの行破棄を確認済みです。検証の過程で、sys_sleep が 16 ビットの符号付き差分で起床判定するため 1 回の呼び出しでは 32767 チック（約 327 秒）までしか眠れないことも分かり、/bin/sleep 側で分割して待つよう直しています。

M8 では、/bin のコマンド 10 個を BusyBox 方式のマルチコールバイナリへまとめました。各コマンドが個別に持っていた起動コードと文字列ユーティリティの重複を無くすためです。romfs にはコマンド名ごとのエントリを残し、全エントリが 1 つのイメージを指します。起動名の受け渡しには、カーネルが argv の先頭に起動名を書く規約（"<name> <args>"）を新たに設け、合体バイナリが先頭の語で処理を振り分けます。難所はデータウィンドウ（256 バイト）で、単純に合体させると各コマンドの静的データ合計が 755 バイトになって溢れるため、全コマンドのバッファを 1 つの union に重ねました（同時に動くコマンドは 1 つだけです）。シェルは PID1 専用なので従来どおり単独のままです。結果として romfs は 15,261 バイトから 11,160 バイトへ減り、イメージの空きは 455 バイトから 4,712 バイトへ増えました。simavr では全コマンドの振り分けと、M7 までの全機能の回帰を確認済みです。

## Serial からのデバッグ

コンソールはシリアル 1 本だけなので、デバッグもすべてシリアル経由です。

### 実機に書く前の検証（simavr）

実機へ書き込む前に、全段階を simavr で検証する方式を取りました。テスト専用カーネルでは、スクリプト化した対話セッションを、受信割り込みと同じ経路で RX リングへ流し込みます（simavr には標準入力を UART へつなぐ機能が無いための工夫です）。これで「起動 → コマンド入力 → 応答」の一連を、書き込みなしで何度でも再現できます。検証済みのイメージだけを実機へ書き込みます。

この段階で捕まえた不具合もあります。シェルが改行を書く際に文字列リテラルを sys_write へ渡しており、ファイルにゴミバイトが混入して cc がエラーになっていました。また cc 自身も、出力ファイル名の組み立てで libc の strcat にリテラルを渡し、無限コピーループに陥りました。後者は simavr の gdb スタブへ avr-gdb を接続し、停止した時点のプログラムカウンタが strcat 内にあることと、レジスタやメモリの状態から切り分けました。いずれも「リテラルはフラッシュにある」という規律への違反が原因で、ucpy／.data の RAM 文字列へ直して解決しています。

### 実機シリアルで見つけた問題

実機側では、貼り付け入力にまつわる 2 件がありました。

1. 受信バッファ溢れ：複数行を一度に貼り付けると、コマンド実行中に届いた文字が受信リング（32 バイト）から溢れて欠落しました（`echo "s...` の `"s` や、`>>` の `>` が消える形で現れました）。受信リングを 128 バイトへ拡大して対策しています（カーネル RAM 1,982 バイトに収納）。それでも、実行中のコマンドに対して長い貼り付けを送ると溢れるため、確実なのは 1 行ずつ送る方法です。
2. Web 版シリアル端末の貼り付け二重送信：自作の Web Serial 端末で、貼り付け先がログ内の文字部分になると、貼り付け処理が 2 経路で発火して同じ内容が 2 回送られていました（`cc /tmp/a.c` が `cc /tmp/a.ccc /tmp/a.c` になる）。端末側のイベント処理を修正済みです。

シリアル端末には Tera Term のほか、Web Serial を使う自作の単独 HTML 端末も使っています。Web Serial はブラウザの枠内表示では許可が届かないため、単独ファイルで開く形が実用です。

## 使い方

### 書き込み

イメージ（linax_uno.bin）を、Arduino IDE 付属の avrdude で書き込みます。

```powershell
avrdude -p m328p -c arduino -P COM13 -b 115200 -U flash:w:linax_uno.bin
```

（COM ポートは環境に合わせて読み替えてください。）

### 接続

シリアル端末を 115200 bps で接続すると、ロゴとバナーが表示され、シェルのプロンプト `/#` が出ます。

```
linaX(uno) 0.8 (ATmega328P)
Welcome to linaX(uno).
Type 'help' for commands.
/#
```

### コマンド

シェルの組み込みは help / cd / pwd / clear / exit です。それ以外は /bin のプログラムを exec します。コマンド履歴もあり、↑／↓キーで直近 2 件を呼び出せます（メモリの都合で、履歴は 2 件・各 40 文字までです）。

```
/bin/sh     シェル
/bin/ls     一覧
/bin/cat    表示
/bin/echo   引数を表示
/bin/uname  システム情報
/bin/ps     プロセス表
/bin/cc     C コンパイラ
/bin/vm     バイトコード実行（通常は exec 経由で自動起動）
/bin/gpio   ピンの入出力
/bin/i2c    I2C バスの操作
/bin/sleep  待ち（単位は 10 ミリ秒。sleep 100 で 1 秒）
```

gpio ではピンを、i2c では I2C バスを操作します。

```
/# gpio 13 out
/# gpio 13 hi
/# gpio 13 read
1
/# i2c scan
i2c scan: 0x3c
/# i2c r 0x3c 1
00
```

（D0／D1 はコンソールの UART と共用です。GPIO として使うとコンソールが止まります。A4／A5 は I2C と共用です。）

実行中のプログラムは Ctrl+C で止められます（終了コード 130 でシェルへ戻ります）。プロンプトで Ctrl+C を押すと、入力中の行が破棄されます。

ps ではプロセスの状態が見えます（R=実行可、B=ブロック中、Z=ゾンビ）。

```
/# ps
pid st ppid
0 R 0
1 B 0
2 R 1
```

### プログラムを書いて実行する

/tmp にソースを書き、cc でコンパイルし、できた .out を実行します。

```
/# echo > /tmp/a.c <<EOF
> a=7;
> print a*6;
> EOF
/# cc /tmp/a.c
/# /tmp/a.out
42
```

1 行ずつ書く場合は echo のリダイレクトでも同じことができます（最初は `>`、続きは `>>`）。

```
/# echo "s=0;i=1;" > /tmp/s.c
/# echo "while(i<=10){s=s+i;i=i+1;}" >> /tmp/s.c
/# echo "print s;" >> /tmp/s.c
/# cc /tmp/s.c
/# /tmp/s.out
55
```

Lチカの例です。内蔵 LED（ピン 13）を 0.5 秒間隔で点滅させます。そのままコピペで使えます。

```
echo > /tmp/a.c <<EOF
while(1){pin 13,1;wait 500;pin 13,0;wait 500;}
EOF
cc /tmp/a.c
/tmp/a.out
```

点滅を止めるときは Ctrl+C を押します。`^C` と `[exit 130]` が表示され、プロンプトへ戻ります。

### cc の言語仕様

- 変数は a〜z の 26 個（16 ビット整数、初期値は 0）
- 代入：`a=式;`
- 出力：`print 式;`、`print "文字列";`
- 演算：+ - * / %、比較 == != < > <= >=、括弧、単項マイナス
- 制御：`if(条件) 文 else 文`、`while(条件) 文`、複数文は { } で囲む
- 待ち：`wait ミリ秒;`（10 ミリ秒単位に切り捨て）
- ピン出力：`pin ピン番号, 値;`（ピンを出力にして値を書きます。Lチカは `while(1){ pin 13, 1; wait 500; pin 13, 0; wait 500; }`）
- 文の終わりの ; は必須です
- main() はありません。ファイル全体がそのままプログラム本体で、上から順に実行されます。関数、配列、for 文もありません

### 制限

- /tmp は 4 ファイル×96 バイトまで。ソースファイルも 96 バイト以内に収める必要があります（空白はほぼ省略できます）
- シェルの行バッファの都合で、入力は 1 行 47 文字までです
- プログラム中の `>` はリダイレクトと解釈されるため、`a>=b` は `b<=a` と書き換えてください
- 文字列を print する行は引用符で囲まないでください（囲むと引用符が取り除かれます）
- メモリ保護はありません（MMU が無いため、分離はウィンドウの入れ替えによる論理的なものです）
- 同時に存在できるユーザプロセスは 2 つまでです
- パイプは未実装です（リダイレクトは echo の書き込みのみ）
